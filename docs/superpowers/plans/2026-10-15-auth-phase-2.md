# Auth Phase 2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add registered email/password sign-in without breaking existing GitHub OAuth or JWT sessions.

**Architecture:** Reuse the existing nullable `users.passwordHash` column and Drizzle adapter. Keep provider metadata and a no-op Credentials authorization callback in the database-free shared config; override that provider in the server config with validated database lookup and bcrypt comparison. Add a separate registration route with explicit HTTP outcomes.

**Tech Stack:** Next.js 16.4 App Router, NextAuth v5 beta, Drizzle/Neon PostgreSQL, bcryptjs, Zod, TypeScript.

**Spec:** `context/features/auth-phase-2-spec.md`

## Global Constraints

- Use `bcryptjs` for hashing; inspection found it missing, so add it as a dependency. Add Zod as a direct dependency for input validation.
- `auth.config.ts`: Add Credentials provider with `authorize: () => null` placeholder.
- `auth.ts`: Override the Credentials provider with actual bcrypt validation logic.
- `POST /api/auth/register` accepts name, email, password, confirmPassword; validates matching passwords and existing users; hashes passwords and creates users.
- Keep GitHub OAuth, JWT sessions, session user IDs, and default Auth.js pages intact. No registration UI, password reset, email verification, or automatic OAuth account linking.
- Existing schema and migration already contain `password_hash`; do not generate a redundant migration. Generate a migration only if an actual schema change becomes necessary.
- All database operations use development branch `ep-silent-bird-b59kwhec`; production is off limits. Verify the runtime connection targets development before HTTP tests that read or write users, and pass the development branch ID explicitly to any Neon tool operations.
- Project workflow defers unit tests: use failing-then-passing HTTP/browser checks, lint, types, and build. Never commit without permission; do not delete test records without permission.
- Builder choices for review: trim names and emails, normalize new emails to lowercase, require a nonempty name (maximum 100 characters), a valid email (maximum 254 characters), and a password of at least eight characters and at most 72 UTF-8 bytes. Never trim or normalize passwords. Use asynchronous bcrypt with cost 12.
- Rate limiting is outside this spec; record its absence as a deployment limitation rather than claiming this change hardens public registration against abuse.

## Review Focus

- Malformed JSON, missing or wrongly typed fields, and mismatched passwords return validation errors without creating users.
- Oversized UTF-8 passwords are rejected instead of silently truncated; password whitespace remains significant.
- Existing OAuth-only users cannot authenticate with a password or have their accounts overwritten by registration.
- Concurrent duplicate registrations produce one user and a controlled conflict response, not an unhandled database error.
- Invalid credentials never create a session; database IDs survive repeat sign-in, and password hashes never enter responses, JWTs, or session objects.

### Task 1: Register users safely

**Files:** Create `src/lib/auth-validation.ts`, `src/app/api/auth/register/route.ts`; modify `package.json`, `pnpm-lock.yaml`. Reuse `src/db/schema/auth.ts` unchanged.

**Interfaces:** Export `signInSchema` and `registrationSchema` from `src/lib/auth-validation.ts` as Zod schemas. Export `POST(request: Request): Promise<Response>` from the route. JSON follows `{ success, data, error }`: 201 returns only `{ id, name, email }` in data; 400 invalid input; 409 duplicate email; 500 generic server failure. Errors never expose submitted passwords or database details.

Select/return only safe user fields. Do not set a session or email verification date.
- [x] Verify HTTP outcomes for valid registration, malformed JSON, null/array payloads, missing/wrongly typed fields, invalid email, blank name, short password, mismatch, and passwords exceeding 72 UTF-8 bytes. Assert 201/400 responses and that rejected inputs do not create users.
